# GEO 서비스 백엔드 개발 수행 내용

## 1. 개발 개요

본 사업에서는 사용자가 웹사이트 URL을 입력하면 대상 페이지의 콘텐츠와 구조화 데이터를 수집하고, 도메인별 GEO(Generative Engine Optimization) 분석 모델을 통해 진단 결과와 개선안을 제공하는 백엔드 시스템을 개발하였다. 단순 URL 점수 산정 기능에 머무르지 않고, 회원 인증, 분석 주문 접수, 비동기 작업 처리, 정적·동적 웹 수집, AI 서버 연동, 결과 보고서 관리, 유료 개선 작업, 결제 및 이용권 관리, 파트너 구독, 완료 알림까지 하나의 서비스 흐름으로 연결하였다.

개발 과정에서는 다음 문제를 핵심 과제로 정의하였다.

- 웹페이지마다 정적 HTML, JavaScript 렌더링, JSON-LD 구성 방식이 달라 동일한 입력 품질을 확보하기 어려운 문제
- GPU 기반 AI 분석 시간이 길어 HTTP 요청 안에서 처리를 완료할 경우 응답 지연과 타임아웃이 발생하는 문제
- 사용자 주문, 실제 분석 실행 상태, 결과 보고서 상태가 하나의 데이터 모델에 섞일 경우 재시도·삭제·만료 처리가 불명확해지는 문제
- 결제 성공, Pack 이용권 지급, 개선 작업 차감, 환불을 각각 처리할 경우 중복 지급이나 잔액 불일치가 발생할 수 있는 문제
- 분석은 완료되었으나 이메일 발송이 실패하거나, 재시도로 같은 알림이 중복 발송될 수 있는 문제
- Spring 백엔드와 Python AI 서버 사이의 요청·응답 규격이 변경될 때 분석 결과가 유실되거나 잘못 분류될 수 있는 문제

이를 해결하기 위해 Java 21, Spring Boot, Spring Security, Spring Data JPA, PostgreSQL을 기반으로 백엔드 구조를 구성하고, Jsoup·Playwright·Flexmark를 조합한 웹 수집 계층, RestClient 기반 AI 연동 계층, 데이터베이스 기반 순차 작업 큐, JSONB 결과 저장 구조, JWT·Google OAuth2 인증 체계를 적용하였다.

## 2. 개념설계 및 전체 구조

시스템은 기능 책임에 따라 다음과 같이 분리하였다.

```text
사용자/파트너
  → 회원가입·로그인·JWT/OAuth2 인증
  → 분석 주문 접수
  → Order 저장 + AnalysisJob 생성
  → 스케줄러가 대기 작업을 순차 점유
  → Jsoup 정적 수집
      → 본문 부족 또는 동적 페이지일 경우 Playwright 렌더링
  → 본문 Markdown 정제 + 문서 유형 분류 + JSON-LD 추출
  → AI 서버 /evaluate 호출
  → 분석 결과·품질 경고·오류 유형 해석
  → AnalysisReport JSONB 저장
  → 상태 조회 및 결과 보고서 제공
  → Notification Outbox 적재
  → 이메일 발송 및 발송 이력 관리
```

상품 기능은 분석 파이프라인 위에 다음과 같이 구성하였다.

```text
무료 Scan
  → 핵심 문제와 우선순위 확인

Remediation Pack
  → 토스페이먼츠 카드/간편결제
  → 페이지 단위 Pack 이용권 지급
  → 위치별 수정 diff·안전 검사
  → 이용권 차감
  → 적용 후 30일 내 재수집 검증 2회

Partner
  → 세금계산서 발행 및 계좌이체 확인
  → 관리 학원 수 기준 월 구독 활성화
  → 학원별 작업 공간·월 사용량·보고서 관리
```

핵심 설계 원칙은 결제 주문과 분석 주문을 분리하고, Pack과 Partner를 하나의 공통 크레딧 모델로 억지로 통합하지 않는 것이다. Pack은 구매한 페이지 수를 소진하는 상품이고, Partner는 매월 갱신되는 학원 관리 권한이므로 데이터 필드, 상태 전이, 만료 기준 및 과금 단위가 서로 다르다.

## 3. 주요 기능, 구조 및 동작 방식

### 3.1 회원·인증 및 접근 제어

이메일 회원가입, 로그인, 비밀번호 변경, Google OAuth2 로그인을 지원하도록 인증 체계를 구성하였다. 비밀번호는 Spring Security의 `PasswordEncoder`를 통해 단방향 암호화하여 저장하며, 기존 평문 비밀번호 계정은 정상 로그인 시 암호화 값으로 전환되도록 호환 절차를 적용하였다.

로그인 성공 시 사용자 ID와 역할을 포함한 JWT를 발급하고, 이후 요청은 `Authorization: Bearer <accessToken>` 헤더로 인증한다. JWT 필터가 토큰의 서명과 만료 여부를 검증한 후 인증 정보를 Security Context에 저장하므로, 프론트엔드가 회원 ID를 요청 body나 query parameter로 직접 전달하지 않아도 된다. Google OAuth2 사용자는 제공자 식별자와 이메일을 기준으로 기존 계정을 연결하거나 신규 계정을 생성한 뒤 동일한 JWT 기반 서비스 흐름을 사용한다.

보고서 상세 조회와 사용자별 목록 조회에서는 로그인 사용자의 ID와 주문 소유자를 대조하여 다른 고객의 분석 결과에 접근할 수 없도록 하였다. CORS 허용 출처, 허용 HTTP 메서드, 공개 인증 경로와 보호 경로도 SecurityFilterChain에서 구분하였다.

### 3.2 분석 주문 접수

사용자가 대상 URL, 사이트명, 서비스 유형, 분석 항목, 담당자 연락처 등을 제출하면 `Order`에 주문 원본을 저장한다. 주문에는 다음 정보를 포함한다.

- 분석 대상 URL과 사이트명
- 뉴스·이커머스·교육 등 분석 도메인
- 분석 항목과 대상 검색엔진
- 담당자명, 이메일, 연락처, 소속
- 사용자 메모
- 외부 노출용 무작위 리소스 키
- 주문자와의 연관관계

주문 저장과 동시에 `AnalysisJob`을 생성하여 `PENDING` 상태로 등록한다. API는 크롤링과 AI 분석 완료를 기다리지 않고 주문번호와 접수 메시지를 반환한다. 이를 통해 사용자는 장시간 브라우저를 열어두지 않아도 되며, 서버는 GPU 처리 용량에 맞춰 작업을 안정적으로 순차 처리할 수 있다.

### 3.3 데이터베이스 기반 비동기 작업 큐

분석 작업은 프로세스 메모리의 단순 비동기 스레드가 아니라 PostgreSQL에 영속화된 `AnalysisJob`을 기준으로 처리한다. 작업 상태는 다음과 같이 구성하였다.

| 내부 상태 | 의미 | 사용자 표시 상태 |
| --- | --- | --- |
| `PENDING` | 접수 후 처리 대기 | `ACCEPTED` |
| `RUNNING` | 수집·AI 분석 수행 중 | `PROCESSING` |
| `RETRY_WAIT` | 일시 오류 후 재시도 대기 | `PROCESSING` |
| `SUCCEEDED` | 보고서 저장 완료 | `COMPLETED` |
| `FAILED` | 최대 재시도 후 종료 | `FAILED` |

스케줄러는 생성 시각이 가장 빠른 작업 한 건을 조회하고, `FOR UPDATE SKIP LOCKED`를 이용해 작업을 점유한다. 여러 워커가 동시에 실행되더라도 같은 작업을 중복 수행하지 않으며, 현재 운용 구조에서는 한 건의 AI 요청이 끝난 뒤 다음 작업을 가져오므로 GPU 서버에 분석 요청이 동시에 몰리는 것을 방지한다.

작업별 시도 횟수, 최대 시도 횟수, 다음 실행 시각, 잠금 시각, 오류 메시지를 저장한다. 일시적인 네트워크·AI 서버 오류는 `RETRY_WAIT`으로 전환하여 재처리하고, 최대 횟수에 도달하면 `FAILED`로 종결한다. 내부의 세부 상태는 사용자 화면에서는 접수·처리 중·완료·실패의 네 단계로 단순화하여 제공한다.

### 3.4 정적·동적 웹페이지 수집

웹페이지 수집은 속도와 정확성을 함께 확보하기 위해 2단계 방식으로 설계하였다.

1. Jsoup로 정적 HTML을 우선 수집한다.
2. `article → main → body` 순서로 핵심 영역을 선택한다.
3. `script`, `style`, `noscript`, `iframe`, `svg` 등 분석에 불필요한 요소를 제거한다.
4. HTML을 Markdown으로 변환하여 문장·제목·목록·표·코드 구조를 최대한 유지한다.
5. 본문이 50자 미만이거나 `Loading...`과 같은 JavaScript 초기 화면만 존재하면 Playwright로 실제 브라우저 렌더링을 수행한다.
6. 렌더링된 DOM도 동일한 정제·변환 경로를 통과시켜 AI 입력 형식을 일관되게 유지한다.

이 방식은 모든 요청에 브라우저를 실행하는 비용을 줄이면서도 SPA·동적 렌더링 사이트에서 실제 본문을 확보한다. 정적 수집과 동적 수집이 서로 다른 결과 형식을 만들지 않도록 공통 `Document → ScrapedData` 변환 절차를 사용하였다.

### 3.5 문서 유형 분류와 AI 입력 정규화

수집한 데이터는 AI 모델이 학습·서빙 과정에서 사용한 입력 구조에 맞춰 정규화한다. `html_text`는 다음 순서의 라벨 형식으로 조립한다.

```text
[DOCUMENT_TYPE]

[TITLE]

[AUTHOR]

[PUBLISHED]

[PUBLISHER]

[MAIN_CONTENT]
```

값이 없는 선택 영역은 생략하고, 문서 유형과 본문은 필수로 관리한다. 문서 유형은 JSON-LD의 `@type`을 우선 사용하며, 정보가 없을 경우 뉴스·이커머스·교육 도메인과 교육기관·강좌 관련 키워드를 이용해 `NEWS_ARTICLE`, `PRODUCT`, `EDUCATIONAL_ORGANIZATION`, `COURSE`, `EDUCATION_ARTICLE` 등으로 분류한다.

페이지 안의 `script[type=application/ld+json]`은 각각 독립적으로 파싱한다. 일부 스크립트가 손상되어도 정상 JSON-LD는 보존하고, 객체와 배열을 하나의 유효한 배열로 정규화한다. JSON-LD가 없을 때도 `null`이나 문자열이 아닌 빈 배열을 전달하여 AI 서버가 항상 동일한 자료형을 받도록 하였다.

### 3.6 AI 서버 연동 계약

Spring 백엔드에서 Python AI 서버로 전달하는 요청은 다음 네 필드로 고정하였다.

```json
{
  "url": "분석 대상 URL",
  "domain": "education | ecommerce | news",
  "html_text": "라벨 구조로 정제한 본문",
  "json_ld": []
}
```

과거 입력에 포함되던 중복 필드와 내부용 메타데이터를 제거하여 런타임 AI 게이트웨이의 `/evaluate` 규격과 일치시켰다. 백엔드는 AI 응답의 `status`, `domain`, 구조화된 `result`, `reason`, `detail`을 수신하고, 품질 경고·본문 길이·문자 정규화 여부·AI가 인식한 JSON-LD 같은 부가 정보도 함께 보존한다.

오류는 하나의 일반 실패로 처리하지 않고 다음과 같이 구분한다.

- 연결 지연 또는 서버 접속 실패: `timeout`
- 요청량 제한: `rate-limited`
- 입력 검증 실패: `invalid-input`
- 잘못된 요청: `bad-request`
- AI 추론 서버 오류: `server-error`
- 분석 가능한 본문 부족: `insufficient_content`
- 모델 응답 JSON 해석 실패: `parse_error`

정상 응답에 품질 경고가 포함된 경우에는 분석 성공으로 처리하되 경고 정보를 보고서에 함께 저장한다. 이를 통해 사용자는 결과를 확인할 수 있고, 운영자는 낮은 본문 품질이나 정규화 이력을 추적할 수 있다.

### 3.7 분석 결과 및 보고서 관리

분석 결과는 `AnalysisReport`에 저장하며, 주문과 1:1로 연결한다. PostgreSQL JSONB를 사용해 다음 세 종류의 데이터를 구분하였다.

- `rawScrapedData`: AI에 전달한 수집·정제 데이터
- `rawAILog`: AI 서버의 구조화 분석 결과와 품질 관련 부가 정보
- `processedResult`: 차트, 요약, 개선 우선순위 등 프론트 표시용 가공 결과

보고서 수명주기는 `AVAILABLE`, `EXPIRED`, `DELETED`로 관리한다. 삭제 요청은 물리 삭제 대신 상태와 삭제 시각을 기록하는 소프트 삭제 방식으로 처리하여 감사와 복구 가능성을 확보한다. 만료 시에는 개인정보와 원시 분석 데이터를 정리할 수 있도록 별도의 만료 상태를 두었다.

주문 실행 상태와 보고서 상태는 분리하였다. 따라서 처리 중인 주문도 진행 상태와 오류 메시지를 조회할 수 있고, 완료된 결과만 보고서로 제공하거나 삭제·만료할 수 있다. 사용자별 보고서 목록은 주문, 작업, 보고서를 결합하여 사이트명, URL, 도메인, 처리 상태, 생성 시각을 제공한다.

### 3.8 무료 Scan과 유료 Remediation의 구분

무료 Scan은 사용자가 GEO 상태를 빠르게 확인하는 진입 기능으로 구성하였다. 점수, 우선순위 상위 문제 3개, 이미지 의존 경고를 제공하되, 상세 위치와 근거는 핵심 문제 1개에 집중한다. 유료 결과를 단순히 가려 놓았다가 결제 후 해제하는 방식이 아니라, Pack 이용권으로 새 Remediation 작업을 생성하여 전체 진단과 실제 수정안을 생성한다.

Remediation Pack 이용권 1개는 페이지 1개에 대해 다음 기능을 제공한다.

1. 전체 문제와 우선순위 진단
2. HTML·JSON-LD·본문의 문제 위치 식별
3. 원문과 수정안의 검토 가능한 diff 생성
4. HTML 구문, Schema 구조, 본문 일치 여부에 대한 안전 검사
5. 사용자가 사이트에 적용한 뒤 동일 URL 재수집
6. 수정 전·후 비교 및 남은 문제 확인
7. 완료 후 30일 내 재수집 검증 2회 제공

개선 작업을 접수할 때 Pack 이용권 1개를 즉시 소진하지 않고 먼저 예약한다. 작업이 성공하면 `CONSUMED`, 처리 전 취소 또는 결과 생성 실패 시 `RELEASED`로 전환한다. 이를 통해 실패한 분석 때문에 이용권이 사라지는 문제와 같은 요청이 중복 차감되는 문제를 방지한다.

### 3.9 Pack 상품과 이용권 관리

Pack은 1·5·20페이지 단위의 소모성 상품으로 구성하였다.

| 상품 | 제공 페이지 | 공급가액 | VAT 포함 결제액 | 이용 기간 |
| --- | ---: | ---: | ---: | --- |
| Pack 1 | 1 | 14,900원 | 16,390원 | 단건 이용 |
| Pack 5 | 5 | 49,000원 | 53,900원 | 12개월 |
| Pack 20 | 20 | 149,000원 | 163,900원 | 12개월 |

Pack 주문에는 상품 유형, 전체 페이지 수, 남은 페이지 수, 실제 결제 금액, 구매 시각, 만료 시각, 결제 상태를 저장한다. 잔여량은 유효한 결제 상태와 만료 여부를 확인한 뒤 차감하며, 사용할 수 없는 Pack 또는 잔액이 0인 Pack은 차단한다.

운영 규모가 커져도 잔액의 원인을 추적할 수 있도록 지급, 예약, 사용, 반환, 환불 보류, 환불, 만료를 불변 원장 이벤트로 관리한다. 먼저 만료되는 이용권부터 사용하는 방식으로 Pack을 선택하고, 잔액 변경과 작업 예약을 하나의 트랜잭션으로 처리한다.

### 3.10 토스페이먼츠 결제

Pack 결제는 토스페이먼츠 한 곳으로 통합하고, 일반 신용·체크카드는 `CARD`, 간편결제는 `EASY_PAY`로 구분한다. 두 방식 모두 프론트에서는 토스 결제위젯을 사용하고, 백엔드는 `/payments/confirm`에서 최종 승인을 처리한다.

결제 안전성을 위해 다음 원칙을 적용하였다.

- 상품명, 이용권 수량, 공급가액, VAT, 결제 총액은 서버 상품 정보로 결정한다.
- 구매 주문 생성 시 가격과 정책 버전을 스냅샷으로 저장한다.
- 프론트가 전달한 승인 금액과 서버 주문의 VAT 포함 총액을 대조한다.
- PG 승인 응답의 주문번호, 통화, 총액, 결제수단을 다시 확인한다.
- 결제 승인 성공과 Pack 이용권 지급을 같은 내부 트랜잭션으로 반영한다.
- 외부 승인 결과가 불명확한 타임아웃은 실패로 단정하지 않고 `UNKNOWN`으로 보존한 뒤 PG 거래 조회로 복구한다.
- 생성·승인·환불 요청은 멱등키를 사용하여 브라우저 재시도와 네트워크 응답 유실에도 중복 결제·중복 지급을 방지한다.

결제 상태는 `READY`, `CONFIRMING`, `UNKNOWN`, `SUCCEEDED`, `REFUNDED`, `FAILED`, `EXPIRED` 등으로 관리한다. 사용자가 일부라도 예약·사용한 Pack은 자동 부분 환불하지 않고, 미사용 Pack만 원 결제수단으로 VAT 포함 전액 환불한다. 환불 중에는 이용권을 별도 보류 수량으로 이동하여 환불과 작업 접수가 동시에 진행되지 않도록 한다.

### 3.11 Partner 구독과 학원 관리

Partner 상품은 Pack 이용권이 아니라 관리 학원 수 기준의 월 구독으로 설계하였다.

| 구독 등급 | 월 공급가액 | 포함 학원 | 주요 조건 |
| --- | ---: | ---: | --- |
| Founding Partner | 290,000원 | 10곳 | 초기 파트너, 12개월 가격 고정 |
| Partner | 490,000원 | 20곳 | 추가 학원 확장 가능 |
| Partner Plus | 990,000원부터 | 50곳 | 프랜차이즈·대형 대행사, 별도 견적 |

`ClientPlan`은 `FREE`, `FOUNDING_PARTNER`, `PARTNER`, `PARTNER_PLUS`로 구성하여 Partner 권한 등급만 표현한다. Pack 1·5·20 수량은 ClientPlan에 넣지 않고 별도 Pack 주문과 잔액으로 관리한다.

`PartnerSubscription`에는 구독 등급, 상태, 기본 및 추가 학원 수, 월 이용금액, 가격 고정 기한, 구매·만료 시각을 저장한다. Founding Partner에는 12개월 가격 고정 기한을 적용하고, 월 갱신 시 다음 이용 기간을 연장한다.

학원은 단순 합계 숫자가 아니라 `Academy` 엔티티로 관리한다. 학원명, 사이트 URL, 대형·소형 구분, 노이즈 필터 설정, 월 사용 페이지, 활성 상태를 저장하고, 학원별 월 기본 페이지 한도를 적용한다. 대형 학원은 외부 광고·배너 제거를 위한 노이즈 필터를 기본 활성화하고, 소형 학원은 자체 홍보 콘텐츠가 분석에서 제거되지 않도록 기본 비활성화한다.

### 3.12 Partner 세금계산서·계좌이체

Partner는 온라인 카드 자동결제가 아니라 B2B 계약에 맞춰 세금계산서와 수동 계좌이체 방식으로 운영한다. Partner 신청, 운영 검토, 청구서 발행, 입금 알림, 실제 입금 대사, 구독 활성화를 단계별 상태로 분리하였다.

고객이 입금 완료 정보를 제출하면 청구서는 `DEPOSIT_REPORTED` 상태가 되며, 이 신고만으로 결제 완료나 Partner 권한을 부여하지 않는다. 운영자 또는 은행 거래내역을 통해 입금자명, 금액, 청구번호를 대조한 뒤 `PAID`로 전환하고 구독을 활성화한다. 이를 통해 허위 입금 신고나 중복 입금 처리로 권한이 잘못 부여되는 것을 방지한다.

Pack의 PG 결제·환불과 Partner의 청구·계좌이체·과오납 반환은 서로 다른 도메인으로 관리한다. 이 구분은 자동 결제 중심 B2C 흐름과 수동 확인 중심 B2B 흐름의 회계·운영 차이를 반영한 것이다.

### 3.13 이메일 완료 알림

분석 요청은 비동기로 처리되므로, 사용자가 결과 화면을 계속 조회하지 않아도 완료 사실을 알 수 있도록 이메일을 기본 알림 채널로 구성하였다. 문자 메시지는 결제 고객의 선택형 보조 채널로 분리하였다.

이메일은 분석 워커 안에서 직접 발송하지 않고 `notification_outbox`에 발송 작업을 저장한다. 리포트 저장과 알림 예약을 같은 트랜잭션으로 처리하여 결과는 존재하지만 알림이 누락되거나, 결과 저장이 취소됐는데 알림만 전송되는 문제를 방지한다.

알림 Outbox에는 주문번호, 채널, 템플릿, 수신자, payload, 발송 상태, 시도 횟수, 다음 실행 시각, 제공자 메시지 ID, 오류 정보를 저장한다. `UNIQUE(order_id, channel)` 제약으로 동일 주문·채널의 중복 알림을 방지하고, 별도 스케줄러가 `FOR UPDATE SKIP LOCKED` 방식으로 발송 작업을 점유한다. 발송 실패는 분석 성공을 되돌리지 않으며, Outbox에서 독립적으로 재시도한다. 최종 분석 실패도 별도 템플릿으로 통지하여 사용자가 무기한 대기하지 않도록 하였다.

### 3.14 배포·운영 및 확장 구조

백엔드와 PostgreSQL은 하나의 애플리케이션 서버에서 시작하되, GPU 분석 서버는 별도 노드로 분리하는 구조를 적용하였다. Spring 백엔드는 주문·인증·데이터 저장·작업 큐를 담당하고, AI 서버는 평가 모델과 도메인별 LoRA 라우팅을 담당한다. 두 서버는 사설 네트워크 연결을 사용하며, AI 서버 주소와 데이터베이스·OAuth2·JWT 자격증명은 환경변수로 주입한다.

초기 운영은 비용을 최소화한 단일 백엔드 VM과 로컬 GPU 서버 조합으로 구성하고, 트래픽 증가 시 다음 순서로 확장하도록 기준을 수립하였다.

1. 분석 요청을 비동기 큐로 전환하여 HTTP 타임아웃과 순간 부하를 제거한다.
2. 큐 대기시간이 기준을 초과하면 GPU 노드를 추가하거나 장애 시 사용할 서버리스 GPU 경로를 연결한다.
3. 유료 고객과 데이터 중요도가 증가하면 PostgreSQL을 관리형 DB로 분리하고 자동 백업을 적용한다.
4. 컨테이너 이미지를 ARM64·AMD64 환경에서 동일하게 배포하고 CI에서 빌드·테스트한다.
5. 스키마 변경은 버전 마이그레이션으로 관리하고, 상태 테이블과 JSONB 구조의 변경 이력을 보존한다.
6. 상태 확인, 오류율, 큐 대기시간, AI 응답시간, 이메일 반송률을 운영 지표로 수집한다.

이 구조는 웹 API 서버와 GPU 추론 서버의 확장 시점을 분리하므로, 사용자 증가에 따라 전체 시스템을 한꺼번에 증설하지 않고 병목 구간만 단계적으로 확장할 수 있다.

## 5. 문제 해결을 위한 상세 수행 방법

### 5.1 계약 우선 개발

Spring DTO나 과거 문서가 아니라 실제 Python AI 게이트웨이의 런타임 규격을 기준으로 요청 필드와 응답 구조를 재정의하였다. 요청 JSON의 최상위 키를 네 개로 제한하고, 정제된 본문 라벨 순서와 JSON-LD 배열 형식을 고정하였다. 고정 HTML fixture와 요청 직렬화 테스트를 통해 라이브 사이트 상태와 무관하게 계약을 검증할 수 있도록 하였다.

### 5.2 도메인 책임 분리

초기에는 주문 상태와 보고서 삭제 상태가 섞일 가능성이 있었으나, `Order`는 고객 요청, `AnalysisJob`은 실행, `AnalysisReport`는 결과 수명주기를 담당하도록 분리하였다. 이 구조를 통해 처리 중 주문도 조회할 수 있고, 결과 삭제가 작업 이력까지 지우지 않으며, 재시도와 보고서 보관 정책을 독립적으로 변경할 수 있다.

### 5.3 느린 외부 작업의 비동기화

크롤링, 브라우저 렌더링, GPU 분석, 이메일 발송을 HTTP 요청 안에서 연속 수행하지 않도록 데이터베이스 큐와 Outbox 패턴을 적용하였다. 분석 큐와 알림 큐는 각각 영속 상태와 재시도 정보를 가지므로 서버 재기동 후에도 작업을 이어갈 수 있다.

### 5.4 빠른 수집과 정확한 수집의 조합

서버 렌더링 페이지는 Jsoup로 빠르게 처리하고, 실제 본문이 부족한 경우에만 Playwright를 실행한다. 모든 페이지에 브라우저를 실행하는 비용과 정적 HTML만 사용했을 때의 누락 문제를 동시에 줄였다. 두 경로가 동일한 정제기를 사용하도록 하여 모델 입력 편차도 최소화하였다.

### 5.5 외부 연동의 불확실성 관리

AI 호출과 PG 승인은 데이터베이스 트랜잭션으로 완전히 묶을 수 없으므로, 타임아웃을 즉시 실패로 간주하지 않고 불명 상태와 대사 절차를 두었다. 요청별 멱등키, 외부 거래 ID, 내부 주문 스냅샷, Outbox를 조합하여 응답 유실·중복 요청·순서 역전에 대응한다.

### 5.6 테스트 및 품질 검증

다음 항목을 단위·계약·통합 테스트 대상으로 구성하였다.

- 회원가입, 로그인, 잘못된 비밀번호, JWT 발급, 기존 비밀번호 마이그레이션
- 정적 본문 채택과 Playwright 폴백 경계
- JSON-LD 개별 파싱, 손상 데이터 건너뛰기, 빈 배열 보장
- AI 요청의 정확한 4개 필드와 라벨 순서
- AI 정상 응답, 품질 경고, 본문 부족, 파싱 오류, 429, 5xx, timeout 분류
- 여러 작업이 들어왔을 때 AI 호출의 순차 실행
- 성공 시 결과 저장과 상태 완료 처리
- 실패 시 보고서 미생성, 재시도 상태와 오류 메시지 기록
- 사용자별 주문·보고서 조회와 소프트 삭제
- Pack 잔액, 만료, 예약·사용·반환 및 Partner 학원 한도

## 7. 사업화 관점의 개발 성과

첫째, 단일 URL 평가 기능을 실제 서비스 운영이 가능한 주문·작업·결과 구조로 전환하였다. 사용자는 분석 시간을 기다리지 않고 요청을 접수할 수 있고, 서버는 GPU 처리량에 맞춰 작업을 제어할 수 있다.

둘째, 웹페이지 유형에 따른 입력 품질 편차를 줄였다. 정적·동적 수집, 문서 구조 보존, JSON-LD 정규화, 도메인별 문서 유형 분류를 통해 AI 모델이 일관된 입력을 받도록 하였다.

셋째, 분석 결과를 단순 점수에서 실행 가능한 개선 작업으로 확장하였다. 문제 위치, 검토 가능한 diff, 안전 검사, 적용 후 재수집 비교까지 연결하여 “진단만 제공하는 도구”에서 “수정과 검증을 지원하는 작업 도구”로 고도화하였다.

넷째, 무료 사용자, 소규모 구매 고객, 다수 학원을 관리하는 파트너를 하나의 제품 체계로 연결하였다. 무료 Scan은 유입, Pack은 페이지 단위 유료 전환, Partner는 반복 관리와 월 구독을 담당한다.

다섯째, 결제·이용권·환불·입금 확인·알림을 상태 기반으로 설계하여 사업 운영 중 발생할 수 있는 중복 결제, 중복 지급, 잔액 불일치, 허위 입금 신고, 알림 누락과 같은 위험을 사전에 통제하였다.

## 8. 사업계획서용 요약 문안

본 사업에서는 웹사이트의 GEO 상태를 자동 분석하고 실제 개선 작업까지 연결하는 Spring 기반 백엔드 시스템을 개발하였다. 사용자가 URL과 분석 조건을 제출하면 주문과 분석 작업을 데이터베이스에 분리 저장하고, 서버는 접수 결과를 즉시 반환한다. 이후 스케줄러가 작업을 순차 점유하여 Jsoup로 정적 콘텐츠를 수집하고, 본문이 부족한 동적 페이지는 Playwright 브라우저 렌더링으로 보완한다. 수집한 HTML은 문서 유형, 제목, 작성자, 발행일, 발행처, 본문 구조를 갖춘 Markdown 형식으로 정제하며, JSON-LD는 스크립트별로 독립 파싱해 유효한 배열로 정규화한다. 정제 결과는 Python AI 서버의 `/evaluate`에 `url`, `domain`, `html_text`, `json_ld` 네 필드로 전달하고, 구조화된 진단 결과와 품질 경고를 PostgreSQL JSONB 보고서로 저장한다. 분석 작업은 대기·처리·재시도·완료·실패 상태로 관리하며, 사용자에게는 접수·처리 중·완료·실패의 단순 상태와 결과 보고서를 제공한다.

기존의 URL 진단 기능은 무료 Scan, Remediation Pack, Partner 월 구독으로 고도화하였다. Pack 이용권 1개로 페이지 1개의 전체 문제 진단, 위치별 HTML·JSON-LD·본문 수정 diff, 안전 검사와 적용 후 30일 내 재수집 검증 2회를 제공한다. Pack 1·5·20은 토스페이먼츠의 카드·간편결제로 구매하며, 서버가 상품 가격과 VAT 포함 승인 금액을 검증하고 결제 성공과 이용권 지급을 원자적으로 처리한다. Partner는 관리 학원 수 기준의 월 구독으로 구성하고, 세금계산서와 계좌이체 대사를 거쳐 권한을 활성화한다. 학원별 사이트, 대형·소형 구분, 노이즈 필터, 월 페이지 사용량을 별도 관리하여 대행사와 웹 제작사가 여러 학원을 반복 운영할 수 있도록 하였다. 분석 완료와 실패 알림은 리포트 저장과 함께 Outbox에 기록하고 별도 발송기가 이메일을 전송하도록 구성하여, 외부 메일 장애가 분석 큐를 막거나 동일 알림이 중복 발송되는 문제를 방지하였다.
